# R5.1 — Dealer identity, domain, role and scoped customer/order data (design)

Status: draft design, no implementation.
Scope: M5 "Dealerisolatie en eigen OpenSEO", plan v1.1 lines 149-156.
Author: Business Empire Hermes (BUS-93).

## 1. Purpose

Two (or more) dealers run on one shared platform without data leaks. R5.1 defines the
foundation that R5.2-R5.4 build on: how a dealer is identified, what domain it owns,
what roles exist, and how customer/order data is scoped so that dealer A can never read
dealer B.

This document is design only. No application code exists yet (see
`docs/plans/M0-source-registry.md`; the docs/plans repo is documentation and planning).

## 3. Dealer identity

A dealer is the tenancy boundary: every user, customer, order, brand and SEO credential
belongs to exactly one dealer.

Proposed entity:

| Field | Type | Notes |
|---|---|---|
| dealer_id | UUID (PK) | immutable tenant key |
| slug | string, unique | human-readable, used in URLs/domains |
| legal_name | string | |
| display_name | string | shown to the dealer's customers |
| status | enum | active / suspended / closed |
| created_at / updated_at | timestamp | |

Identity and authentication are shared, not per-dealer: one auth service issues a token
that carries the dealer_id as a server-verified tenant claim. This matches the plan's
dependency note (line 183) that CRM/Social/Content/Ad Intelligence can run partly in
parallel only after "gedeelde auth/tenant-contracten" (shared auth/tenant contracts)
are agreed.

Every tenant-scoped table carries a `dealer_id` foreign key. A record without a
dealer_id is not readable by any dealer.

## 4. Dealer domain

Each dealer owns one or more domains (or subdomains). The domain is how a dealer's
customers reach it and is the anchor for R5.3 (per-dealer OpenSEO/domain dashboard).

Proposed model:

- `dealer_domain` entity: `domain_id`, `dealer_id` (FK), `hostname`, `verification_status`
  (pending / verified), `verified_at`, `is_primary`.
- Ownership proof: DNS TXT (or CNAME) challenge before a domain is treated as verified;
  an unverified domain must not serve dealer content or accept dealer-scoped writes.
- Mapping is one dealer -> many domains; a domain belongs to exactly one dealer
  (enforced unique on hostname).

## 5. Dealer role

Role-based access control scoped to the dealer tenant. A role grants access only inside
the dealer it is granted for; no role crosses a dealer boundary.

Proposed roles (dealer tenant):

| Role | Meaning |
|---|---|
| dealer_owner | full control of the dealer tenant, including billing and staff management |
| dealer_admin | manages the dealer's configuration, domains, users |
| dealer_staff | operates day-to-day (orders, customers, content) |
| dealer_viewer | read-only within the dealer tenant |

Platform roles (platform_admin / support) are separate and are the only principals that
can act across tenants, and only where explicitly authorized. They are not granted by
dealer-side logic.

Role assignment is a row in `dealer_membership` (dealer_id, user_id, role). A user may
be a member of multiple dealers but always acts in exactly one dealer context per
request; the active context is resolved from the token, never chosen client-side.

## 6. Scoped customer/order data

Every customer and order is owned by a dealer:

- `customer`: customer_id, dealer_id (FK), ...
- `order`: order_id, dealer_id (FK), customer_id (FK), ...

Isolation is enforced in three layers (defense in depth):

1. Authentication — the access token carries the dealer_id tenant claim; the claim is
   validated and signed server-side and never trusted from the client.
2. Application — a tenant-context middleware resolves the active dealer_id from the
   authenticated principal and attaches it to every data operation; ORM/data-access
   paths default to the tenant filter and require an explicit override to omit it.
3. Data — every tenant table is scoped by `dealer_id`; the database enforces it with
   row-level security (a policy `dealer_id = current_tenant()`), so a missing or wrong
   application filter still cannot return another dealer's rows.

Cross-tenant access is denied (not merely hidden): a request for another dealer's
customer/order returns "not found" or "forbidden", never data.

## 7. Acceptance mapping (R5.1 portion)

- "Dealer A kan geen gegevens van B lezen" -> negative isolation tests: dealer A
  attempts to read/list/update dealer B's customer and order records and receives a
  denial. Covered by R5.1.
- "…geen SEO-credentials van B" -> R5.3/R5.4 scope; R5.1 provides the tenant claim and
  scoping rule those results reuse.
- "€0-SEO-budget werkt voor gratis functies" -> R5.4.
- "centrale updates wissen geen dealerdata" -> R5.2 template versioning plus a
  tenant-migration safety rule that central changes are additive and never overwrite
  dealer-scoped rows.
