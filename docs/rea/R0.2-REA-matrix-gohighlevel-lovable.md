# R0.2 — REA matrix: GoHighLevel and Lovable

Status: research deliverable, no implementation.
Task: BUS-20 (`R0.2: REA-matrix GoHighLevel + Lovable`).
Date of evidence retrieval: 2026-10-23 (all URLs fetched on that date).
Scope: Reverse-Engineering-and-Assessment (REA) of two external platforms against the
capabilities the Business Empire plan asks for: GoHighLevel for social, CRM and telephony;
Lovable for visual generation and preview.

This document answers one question per row: *what can we rely on, what do we merely assume,
and what do we not know yet?* Nothing here authorises a purchase, a paid API call, an account
signup, or code. Rows that need live access are recorded as `MISSING-ACCESS` with the owner and
the action that would unblock them.

---

## 1. Method

### 1.1 Allowed sources

Only sources that are public and require no login, no API key and no payment were used:

1. Vendor documentation sites (`docs.lovable.dev`, `help.gohighlevel.com`).
2. The vendor's own public developer documentation repository
   (`github.com/GoHighLevel/highlevel-api-docs`) and public discovery documents
   (`.well-known/oauth-authorization-server`).
3. Public pricing pages, used only for pricing *structure*, not for exact figures (see D-11).

Excluded by policy: logged-in product UI, trial accounts, reseller/partner portals, paid API
calls, scraped customer data, third-party blog posts, YouTube tutorials, and any source that
requires accepting a contract. Where a fact only exists behind a login, the cell is
`MISSING-ACCESS` — it is never filled in from memory or inference presented as fact.

### 1.2 Markers

| Marker | Meaning |
| --- | --- |
| `PROVEN` | Stated by a public source that was fetched and read during this task. The claim is about **what the documentation states**, not about observed runtime behaviour. |
| `ASSUMPTION` | Plausible inference from adjacent evidence. Not stated by a source. Must be validated before it can carry a P0 decision. |
| `UNKNOWN` | No reliable public information found. Not guessed. |
| `MISSING-ACCESS` | Cannot be established without an account, credential or paid plan we do not have. |

A `PROVEN` cell never means "we tested it". Every `PROVEN` cell that matters commercially is
still tied to a feasibility test in §4, because documentation and product drift apart.

## 4. P0 integrations and their feasibility tests

Definition: **P0** = an integration without which the R8.4 demo (one webshop, two dealer sites,
SEO dashboard, order-to-supplier, Odoo booking) cannot be shown. Each P0 gets exactly one
decisive test. None of these tests is executed in R0.2 — they are specified so they can be run
in one sitting once access exists, and none of them spends credits except where stated.

### F1 — GHL: publish one social post to one channel via API
- **Proves:** cell 2.3 (API write for social posts) and 1.2 (scoped token).
- **Precondition:** one sandbox location + private integration token with `socialplanner/post.write` only; one connected Facebook page (client-owned).
- **Steps:** create a draft post via the API for a future timestamp; read it back; confirm it appears in Social Planner; let it publish; capture the post id and the public URL.
- **Pass:** post id returned, read-back matches, published post visible on the channel.
- **Also observes:** whether the endpoint rejects narrowly-scoped tokens (scope enforcement).
- **Cost:** free API calls. **Owner:** Hermes. **Blocked by:** B-1.

### F2 — GHL: contact + opportunity round-trip with our CRM of record
- **Proves:** cells 3.1–3.4.
- **Steps:** create a contact with three custom fields, create an opportunity in a named pipeline stage, update the stage, then delete the contact. Read each object back after every write and record which fields the API silently drops.
- **Pass:** all three custom fields survive; stage transition is observable; deletions confirmed by 404 on read.
- **Cost:** free. **Owner:** Hermes. **Blocked by:** B-1, B-3 (custom-field schema).

### F3 — GHL: inbound SMS → signed webhook → our endpoint
- **Proves:** cells 4.1–4.3, 6.1–6.5.
- **Steps:** register a marketplace-app webhook for `OutboundMessage`, send an SMS to the sandbox number from a controlled handset, verify `x-wh-signature` with the published public key, reject one tampered copy, then de-duplicate by `webhookId` on a forced retry.
- **Pass:** signature verification succeeds on the genuine payload and fails on the tampered one; replay is idempotent.
- **Also observes:** retry/backoff timing, which is the input for our queue design.
- **Cost:** one SMS segment + one inbound SMS. **Owner:** Hermes. **Blocked by:** B-1, B-2, B-4.

### F4 — GHL: place a call, retrieve recording and transcript
- **Proves:** cells 5.1–5.4.
- **Steps:** enable call recording + transcription on the sandbox location, place a 30-second call, wait for the transcript-generated event, fetch the transcript via API if a read endpoint exists.
- **Pass:** transcript text is retrievable by API, or the absence of a read endpoint is documented (which flips 5.4 to PROVEN-absent and forces a download-and-store design).
- **Cost:** well under one minute of voice plus transcription fee. **Owner:** Hermes. **Blocked by:** B-1, B-4.

### F5 — Lovable: publish a Git-synced project through the API
- **Proves:** cells 13.1–13.4, 14.1–14.3, 11.2.
- **Steps:** create a workspace project by hand, connect it to a fresh repo we own, make one commit in the editor, confirm the commit lands in the repo, then call publish via API with a workspace key and poll publish status until `completed`; finally map a test subdomain.
- **Pass:** publish status reaches a terminal success state, the site serves our commit's content, custom domain resolves over HTTPS.
- **Also observes (key):** whether *any* documented call can create a project — expect "no", which confirms 12.2 empirically.
- **Cost:** one small build (paid credits, requires Orchestrator approval). **Owner:** Hermes. **Blocked by:** B-5.

### F6 — Lovable: brand-fidelity and portability check on generated output
- **Proves:** cells 14.3–14.5, 16.2–16.3, 17.3.
- **Steps:** build one landing page from the LavaBean brand tokens, clone the synced repo, run `npm ci && npm run build`, run our linters, and score the page against the brand guide on typography, colour, spacing and layout at three breakpoints.
- **Pass:** repo builds outside Lovable without manual fixes; ≥4 of 5 brand dimensions match; no high-severity SAST findings.
- **Cost:** one build (paid credits). **Owner:** Hermes. **Blocked by:** B-5, B-6 (brand tokens, R2.1).

## 6. Assessment

**GoHighLevel — feasible, with one commercial gate.** Every capability the plan needs (social
publishing scopes, CRM writes, SMS/WhatsApp inbox, native telephony with per-minute billing,
signed webhooks, per-location tenancy, SaaS provisioning endpoints) is documented in public
sources. The gate is licensing: agency-level authorisation is tied to Agency Pro, and the
consumer-side tariffs (SMS, voice, numbers) are usage-priced, so unit economics depend on
volume. Technical risk is concentrated in three places — the unverified social-post endpoint
(2.3), signature verification that does not identify the app (6.4), and undocumented delivery
semantics (6.7). All three are answered by F1 and F3 for the price of a few SMS segments.

**Lovable — usable, but not as a generation API.** The public API is a management and publishing
API: workspaces, projects (read/update/delete/embed), publish/unpublish/status, analytics,
members, security. There is no documented way to create a project or submit a prompt. Code
portability is genuinely good (two-way Git sync into a repo we own, documented self-hosting),
custom domains need a paid plan, and build cost is credit-based and variable. The honest
conclusion: Lovable can host and publish what a human or an agent produces in its editor, and
its output is not locked in — but it cannot be dropped into an automated "generate a storefront
per client" pipeline today.

**Recommendation for R0.3.** Do not design an architecture that assumes headless Lovable
generation. Either (a) treat Lovable as a designer-facing tool whose output reaches us through
Git, or (b) re-scope visual generation to a provider with a documented generation API. For
GoHighLevel, proceed to a sandbox and run F1–F4 before any commercial commitment; the cost of
being wrong there is a few euros, and the cost of being wrong on a licence tier is a contract.
